# 教学写法

## 读者需要建立怎样的理解

开头保留用户的问题，用两三个结论定位系统。之后以一个任务串起文件、配置、执行与结果。先教完成当前理解所需的前置知识，技术细节按读者目标增加。章节数量由系统和任务决定，目录树与组件清单放在查阅部分。

每个重要环节写成完整因果句，明确：
- **执行者**：用户、本地脚本、宿主、云平台、模型、工具服务或审核人员。
- **输入与状态**：文件、配置、请求、标识、工作目录及必要生效条件。
- **动作**：读取、替换、序列化、上传、创建、调用、持久化、返回等真实动作。
- **输出与接收者**：产生了什么，下一环节拿到什么，为什么要交给它。

不强制把每段改成字段表。用自然语言把这些要素连接起来；有多条可比记录时再用表。

## 用例与中间状态

选业务上有意义且能被源码支持的最小例子。保留同一 request_id、文件名或对象字段贯穿链路；与主题无关的参数省略并标明。例子属于简化或虚构时，说明省略了什么，不使用真实凭据或未授权的业务数据。

配置或数据变换提供转换前与转换后。例子需要兼容真实结构；解释为何要转换、谁负责转换、是否修改原文件、何时才能观察到结果。

例如，原句“读取 system.file 并内联 Prompt”缺少读取者和内容：
1. 本地配置的 `system.file` 保存一个角色文档的路径。
2. 部署脚本打开这个文档，取出文字。
3. 发给平台的请求用实际文字替换路径；平台无法直接读取用户电脑的相对路径。
4. 平台登记角色配置。是否开始任务，要继续检查创建会话和提交输入的代码。

这是写法示例，不代表所有项目都采用这些字段或部署行为。实际工程中找到读取代码再使用该解释。

首次出现专有术语时，先讲当前作用再给名称。例如“连接外部工具服务的协议，MCP”。普通编程概念是否解释由读者知识决定，避免对专业读者重讲整套语言基础。缩写翻译后继续说明用途，不能只把 GL 换成 General Ledger。

## 文件说明怎样写

对读者会接触或影响主线的特有文件，解释内容、读取者、使用时机和可观察效果。相同后缀不保证作用相同；一个项目的 manifest 是安装描述，另一个可能是部署请求。以实际读取者决定解释。

区分：
- 自然语言提示词与可执行程序。
- 程序可识别的字段与单纯文档约定。
- 角色名称与运行中的实例或会话。
- 方法说明与工具能力；提示词禁止与执行权限限制。
- 配置声明、有效配置、程序执行与外部系统结果。
- 部署准备、资源创建、发起任务、执行、输出与人工审核。

## 图与讲解如何配合

先用正文建立概念，再用图呈现关系。每张图解决一个问题：
- 总览：哪些部分负责什么，外部边界在哪里。
- 顺序：一次任务谁调用谁，携带什么标识，何时等待或返回。
- 数据流：某字段怎样转成另一表示，在哪里存储。
- 生命周期：对象当前什么状态，什么事件能改变状态。

图中的名字先在正文定义，箭头注明调用、委派、返回、数据或控制含义。异步边界不能画成已经完成的同步调用。实际运行未观察时，标题或读图说明明确是源码/配置关系。概念图中的抽象组件不冒充真实服务。

大型图按系统、链路、模块拆分；跨图保留同一名称和标识。没有必要展示全仓所有函数。

## 审阅与反馈

逐段做初读者审阅，不只搜索“术语是否存在”：
1. 遮住源码链接，读者是否知道主语是谁、输入是什么、结果是什么？
2. 字段和值是否先解释用途？相对路径以谁为基准？示例值是否符合真实格式？
3. 叙述跳过了哪些必要状态？一个 API ID 是否被误写成已经执行完任务？
4. 角色要求是否被当成权限或实际结果？引用是否支持结论强度？
5. 正常路径与失败/配置条件是否解释了可观察的不同结果？
6. 图与正文是否一致？证据不足是否出现在会影响理解的对应位置？
7. 自检是否要求读者预测或复述机制，而不是背目录名？

给重要段落一个改变条件的练习与答案，例如“修改本地配置后，已创建的远端实例会自动更新吗？”答案必须由实际实现决定。阅读学习路线时，优先“理解入口 → 看懂一条执行链 → 理解设计取舍 → 能预测变化”，再提供源码深读路线。

用户指出仍不懂时，从第一个缺失前提开始修复，使用更具体的输入与结果。不要靠追加大量术语定义或拉长全部段落回应。若用户要求通篇改写，则应用到所有章节。

静态检查不能证明教学有效。最终明确已核对的内容、未完成的运行/渲染证据；不要声称读者已掌握。允许读者用首个不懂的步骤继续反馈，不把答题作为完成文档前的必需审批。
