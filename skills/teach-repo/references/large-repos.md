# 大型仓库与长任务

## 先明确完整性的含义

用户说“讲整个工程”，通常需要系统层面的地图与能解释设计的代表流程。明确交付覆盖系统关系、主线和关键变化条件；逐文件细节可以逐层展开。不要偷偷把全面请求缩成一个小模块，也不要把全量文件列表称为全面理解。

没有单一文件数量阈值能决定复杂度。当一次上下文无法容纳多个模块、存在多个部署单元或主线跨仓库时，采用下面的分层流程。盘点脚本的默认上限是工具资源限制，可以按任务调整，不是“超过一万文件就判定超大项目”。

## 模块地图与覆盖状态

先查构建/工作区声明、服务注册、部署单元、业务域和公共协议。模块边界来自这些证据，不只依据一级目录。地图包含职责、入口、外部依赖和状态：
- **已追踪**：主线从入口到输出有对应证据。
- **局部核实**：读取了一些实际逻辑，仍有明确缺口。
- **仅文档说明**：信息来自 README/设计说明。
- **未探索**：只有路径或名称。
- **外部/受阻**：另一个仓库、生成器、服务或有效配置不可访问。

记录选择依据。重要模块不能因为难读被排除；先保留其位置与未确认边界，然后按风险与读者目标继续取证。

## 代表链路与逐层加深

选择与读者问题最相关、跨越主要边界的一条正常流程；再选择一个改变结果的条件，如配置关闭、异步失败、缓存未命中、授权拒绝或回退。不是所有场景都要建立同样多的样例。

沿链路读取调用者、接口实现、配置读取点、事件注册、存储与返回代码。接口定义和实现绑定分别确认。遇到跨语言 RPC、MQ、任务队列、插件加载器时，将边界两端作为不同证据项；追踪 request_id/call_id/task_id 的产生、传播与消费。

教学层级：
1. 系统地图：整个范围里各部分与外部系统的关系。
2. 代表流程：一个输入如何走到结果，哪些阶段有证据。
3. 模块讲解：模块内部状态、数据、实现和设计取舍。
4. 深读索引：源文件、测试、版本与尚待追踪问题。

不把分层包装成所有模块已经验证。生产配置缺失时，代码默认值和生效值分开；注册代码在另一仓库时，不声称消费者实际运行。

## 上下文与资源管理

优先 `rg --files` 和范围限定的 `rg`，先读文件名、入口与少量相邻源码，再扩大范围。排除依赖、构建产物、二进制、生成文件和无关数据；生成代码只在主线需要时读相关片段，先找生成器、schema与生成命令。

设置一轮探索的明确边界：候选模块、要回答的问题、文件/时间预算、继续条件。预算耗尽后保存已确认结论和未覆盖点，继续下一轮；用户明确预算则遵守。脚本截断时检查 `inventory_complete` 与 `stop_reasons`，禁止推断总文件数或未出现模块不存在。

若有可用子 Agent 且宿主允许委派，可对互不依赖模块开展**并行只读探索**。分配模块与问题，限定输出为职责、入口、引用范围、版本、未知项；主 Agent 统一命名、证据强度和跨模块链路，拥有最终文档。不要让每个子 Agent 都扫描整个仓库或直接并行改同一教材。没有委派能力时按同样边界顺序推进。

## 跨轮与更新

保存一个简洁探索记录，包含目标/读者、源码版本、主线对象、已读入口、关键结论与引用、待确认边界、下一轮动作。恢复时核对记录和相关文件；哈希变化使对应结论待重验。

更新时定位变化影响的调用链与章节，重新核对引用、图和自检答案。新旧提交不混用；脏工作区使用文件哈希绑定本次证据。盘点是结构快照，不提供历史版本或生产运行证明。
